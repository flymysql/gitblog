写给完全没用过 AI 编程工具的人。全程不需要会写代码，你只要会提问、会看结论。

官方资料：DSH 文档 · DeepSeek API 文档 · 开放平台

一、装 DSH（5 分钟）

它是什么：跑在你自己电脑上的 AI 助手。能读你指定的文件夹、能自己跑命令、动手前会问你。聊天机器人给你答案，它给你结果。

下载：打开 https://github.com/anywhere-labs/dsh-desktop/releases，在最新版（写本文时 v2.0.15）的 Assets 里按系统选：

你的系统 下哪个文件
Windows 64 位 DSH-Desktop-2.0.15-x64-Setup.exe
macOS（Intel / Apple 芯片都行） DSH.Desktop-2.0.15-universal.dmg
Linux ...-amd64.deb 或 ...-x86_64.appimage

安装包 200~500 MB 是正常的（自带运行时，不用另装 Node.js）。装完双击打开即可。

  • Windows 弹「Windows 已保护你的电脑」→ 更多信息 → 仍要运行
  • macOS 提示无法验证开发者 → 系统设置 → 隐私与安全性 → 仍要打开

第一次打开：只认这三个地方

  1. ① 左下「选择工作区」 —— 选一个文件夹（比如放插件、放代码的那个目录）。 没选之前输入框是灰的、点不动，这不是坏了 —— 这是新手最容易卡住的地方。它只看得到你选中的那个文件夹。
  2. ② 输入框 —— 选中工作区后才能输入。新任务的第一次提问，建议永远加一句 先不要修改任何文件。
  3. ⚙ 设置 → 模型 —— 填 API Key（下一节）。

一个小习惯：一个任务开一个新会话，别把改插件和写周报混在一起。

二、配模型：注册 → 充值 → 取 Key（5 分钟）

从 https://platform.deepseek.com/ 开始（注意：和聊天版 chat.deepseek.com 不是一个站，只有开放平台里才有 API Key）：

  1. 注册登录：手机号 / 邮箱收验证码
  2. 充值：左侧「充值」，选金额，支付宝 / 微信扫码 —— 第一次充 ¥20 就够用很久
  3. 创建 API Key：打开 https://platform.deepseek.com/api_keys → 创建 → 起个名字（比如 dsh）

⚠️ 创建出来的那串 sk-… 只显示这一次，立刻复制。它是你的钱包，不要发给别人、不要粘进代码或 GitHub（GitHub 上有机器人 7×24 扫这种字符串，几分钟就能刷爆）。泄露了立刻去 API keys 页删掉重建。

然后回到 DSH：

设置 → 模型 → DeepSeek 卡片粘 Key → 保存。立即生效，不用重启；密钥只写不读（页面上只显示脱敏结果）。

配好后先验证一句，别省这一步：

请回答：1+1 等于几？只回答数字。

报错对照：401 = Key 不对（检查空格）；Insufficient Balance = 该充值了；MISSING_CREDENTIAL = 回设置里重新保存一次。

三、怎么"用嘴"让 AI 干完一整件活

四条心法：

  1. 一次只让它做一件事：先读懂 → 再定位 → 再修 → 再打包 → 再验证。别一句话全交代完。
  2. 把它逼到"证据"上：文件 + 行号 + 可复现命令，缺一不可。
  3. 让它写脚本自证：能跑的检查 > 口头保证。
  4. 让它交代边界：哪些验证过、哪些只是猜。

真实案例：三句抱怨 → 四类问题

用户原话（客服转来的，一字未改）：

明 上次那个新版他们说用不了 还有旧版也出一些问题 证书上传不成功，或者跳过之后第二遍再上传识别不到原来上传失败的好像

素材就是两个文件：用户手上的 淘宝证书自动上传2.0.crx，和下载页上发布的 taobao-cert-uploader-v1.3.1-360-signed-v2.crx。

第 1 轮｜读懂（只读，不许改）

把 淘宝证书自动上传2.0.crx 解包到 unpacked/（注意 crx 不是普通 zip，前面有一段头部），列出完整文件树并说明每个文件干什么，再画一张"用户操作 → 哪个文件在处理"的主流程图。不要修改任何东西。

结果：一个 22 个文件的插件结构。顺带发现一个可疑点——文件名写着「2.0」，manifest.json 里的版本号其实是 1.2.5。

第 2 轮｜把抱怨拆成可验证的假设

把上面那句抱怨拆成 3 条可以用代码或命令验证的技术假设，每条写清楚：假设是什么、在哪段代码能看到证据、用什么方法证实或推翻。先不要下结论。

它给出三条（后来全部命中）：

# 假设 怎么验证
1 "用不了"可能是安装包本身装不上，而不是功能有问题 解析 crx 文件头 + 按 Chrome 规则验签
2 "上传不成功"是页面上找不到元素，或按钮点不动却没报错 查选择器是否写死、点确定前有没有校验
3 "第二遍识别不到"是失败的单被误标成"已完成"，之后永久跳过 查完成记录的写入条件与过滤逻辑

第 3 轮｜找证据（这一轮直接破案）

写一个 Node 脚本解析 crx 文件头、按 Chromium 的规则验签（注意签名载荷的长度定义），然后跑这几个包，把结果做成对照表。

顺着线索回发布脚本一看，凶手自己招了：

// 旧版发布脚本里"签名失败就降级"的兜底
const crx = Buffer.concat([Buffer.from('Cr24'), Buffer.from([2,0,0,0,0,0,0,0]), zipBuf]);
// → CRX version=2 + 长度全 0 的伪头部，Chrome 第一步校验就拒绝

第二个包更冤：它想修，注释还写着「参考 chromium 源码」，但把长度取错了——

// ❌ 错的：用了整个 CrxFileHeader 的长度（581）
new DataView(size.buffer).setUint32(0, placeholderHeader.length, true);

// ✅ 对的：用 signed_header_data 自己的长度（18）
new DataView(size.buffer).setUint32(0, signedData.length, true);

第 4 轮｜修 + 自检

修上面三处，每改一处都在同一轮里配一个不依赖浏览器、不依赖淘宝的测试用例。

  • 跳过不重试 → 完成判定收敛成一个函数：
function tcbIsCompletedShipRecord(record) {
  if (Number(record.certFailed) > 0) return false;           // 有失败 → 必须重试
  if (record.skipReason === 'heartbeat-timeout') return false;
  if (record.noCertButtons) return false;                    // "没扫到按钮" ≠ "没有证书"
  return record.certUploaded > 0 || record.certSkipped > 0;  // 至少成功一个才算完成
}
  • 上传不成功 → 上传控件加 4 级兜底选择器；证书编号填入后回读校验；注入图片后检查 input.files；点「确定」前等按钮变成可点击，一直是禁用就直接报清楚缺了哪一项（证书编号为空 / 检测机构未选择）
  • 新版装不上 → 修正签名载荷 + 打包时自检，验不过就抛错；发布脚本删掉"伪格式兜底"，改成直接失败退出

自检跑出来是这样（17 项全过，其中两条是这么写的）：

✅ 正解：LE32(len(signed_header_data)) + signed_header_data + archive → 验签通过
✅ ❌ 1.3.1 的错误写法：LE32(整个 header 长度) → 验签失败（Chrome 拒绝安装）

把踩过的坑写成"必须失败"的用例——以后谁手贱改回去，一跑测试就红了。

第 5 轮｜打包 + 发布前门禁

给我 tools/pack.mjs：打出 zip 和签名 crx；复用插件自己的打包代码，不要在脚本里另写一份；打完自动解包、对所有 js 做语法检查、验签；私钥只从仓库外读、绝不进安装包；任何一步失败就直接退出，不要"降级继续"。

✅ taobao-cert-uploader-v1.4.0-chrome.zip (87613 bytes)
✅ taobao-cert-uploader-v1.4.0-360-signed.crx (88206 bytes, 扩展ID jkmkapiplbcmnoghdphbbcbfebjdlbib)
🔎 ✅ PASS  version=3 签名=有效 ｜ 解包成功，14 个 js 语法检查通过

第 6 轮｜让它交代边界

列出：哪些结论是真机验证过的、哪些只是代码推理；用户升级要注意什么；还有什么风险没排除。

这一轮它给出三个我没注意到、但必须转达给用户的点：

  1. 升级前先卸载旧版。两个安装包的签名私钥不同 → 扩展 ID 不同 → 浏览器眼里是两个不同的插件，会同时往页面里注入按钮、互相打架；而且新插件的本地记录（已完成订单、证书自增序号）是空的。
  2. 私钥不该随包分发。旧版把签名私钥 export-key.dat 打进了 CRX 发给所有人——等于把公章复印给每个用户。
  3. 诚实交代：上传那三处加固只到「代码推理 + 单元自检」，没在真实淘宝卖家页面上跑过端到端（要登录卖家账号 + 真实订单）。所以发布后要先小批量试，出问题用插件自带的「📦 导出日志包」把现场发回来。

旧版也出问题 后来那个"签名修好了"的包，签名载荷长度算错，照样装不上 ✅ 修好

新包已经放进 cloudbase/static/packages/，发到下载页只要一条命令：

node cloudbase/publish-extension.mjs --version 1.4.0

它自带门禁：签名不对会直接失败退出，不会再发出去一个装不上的包。

五、小白避坑清单

用 DSH 的时候

  1. 没选工作区，输入框是灰的 —— 不是坏了
  2. 一个任务一个会话
  3. 新任务先只读，加一句"不要修改任何文件"
  4. 权限弹窗看清楚再点，那是安全阀
  5. 模型先用 deepseek-flash，便宜且够用
  6. 想省钱就避开工作日 9–12、14–18

关于 API Key

  1. Key 只显示一次，创建后立刻复制
  2. 别往聊天框、代码、GitHub 里粘；泄露立刻删掉重建
  3. 第一次充 ¥20 就够跑很久

让 AI 干活

  1. 分轮次：读懂 → 定位 → 修 → 打包 → 验证
  2. 要证据（文件 + 行号 + 可复现命令），不要"我觉得"
  3. 要自检脚本，不要"我改好了"
  4. 要它自己说清楚"哪些没验证过"
  5. 把踩过的坑写成测试用例

发给用户的东西

  1. "我能打开" ≠ "用户能安装"：先验证产物合法，再去 debug 功能，顺序反了会白干几天
  2. 不要写"失败就降级成另一个格式"的兜底 —— 伪格式比明确报错糟糕一百倍
  3. 尽量别换签名私钥，换了等于换了个新插件
  4. 私钥是公章，不要随包分发

附：顺手修掉的两个博客构建脚本坑

这两个不在需求里，是 AI 为了能验证自己的改动而被迫发现的：

  • Windows 上读不到本地统计数据：代码用 new URL('..', import.meta.url).pathname 取项目根目录，在 Windows 上会得到 /D:/work/blog/ 这种带前导斜杠的路径，existsSync 恒为 false → 本地构建静默丢掉全站 PV 和评论数据。改用 fileURLToPath。
  • 同一天多篇文章的网址会随机器变化：决定 YYYYMMDD-2、-3 顺序的排序用了 localeCompare，它的结果跟系统语言有关（中文按拼音、英文按码点），同一份代码在不同机器上会把已有文章的网址互换。改成码点比较后，实测旧文章 URL 变化数为 0。

一条经验：凡是"排序 + 生成 ID/URL"的地方，都要警惕 locale、时区、文件系统返回顺序这三件事。

全文最重要的一句：让 AI 明确告诉你 —— 哪些它验证过了，哪些它只是在猜。
