第一部分：把 DeepSeek Harness 装上

它到底是什么

DeepSeek Harness（简称 DSH）不是一个"聊天网页"，而是一个跑在你自己电脑上的 AI 助手。区别在这三点：

  1. 它能碰你的文件：你把它指到一个文件夹（比如 C:\Users\你\Downloads），它可以自己读里面的文件、改里面的代码、新建文件。
  2. 它能跑命令：需要解压、需要计算哈希、需要装依赖，它自己敲命令，然后把输出读回来看。
  3. 它会问你：要删文件、要联网、要执行有风险的操作时，它会停下来先征求你同意。

一句话：聊天机器人给你答案，Harness 给你结果。

如果你只想"问问题"，用网页版 DeepSeek 就够了。装 Harness 的意义是——你有一堆"烂摊子"要处理（比如一个不知道谁写的插件、一堆日志、一个报错的脚本），你想让 AI 自己动手干完。

下载安装（Windows / macOS）

有两种用法，小白选第一种：

方式 A：桌面版安装包（推荐）

打开 Releases 页面：

https://github.com/anywhere-labs/dsh-desktop/releases

在最新一版（写本文时是 v2.0.15）的 Assets 里按系统选：

你的系统 下载哪个文件
Windows 64 位 DSH-Desktop-2.0.15-x64-Setup.exe
macOS（Intel / Apple 芯片都行） DSH.Desktop-2.0.15-universal.dmg
Linux (Debian/Ubuntu) DSH-Desktop-2.0.15-amd64.deb
Linux (其他) DSH-Desktop-2.0.15-x86_64.appimage

页面里还有一条 DSH NEXT 系列（DSH-NEXT-2.0.15-next-...），是同一套东西的"下一代"分支，功能更新更快、可能更折腾，小白先用标准版 DSH-Desktop。

安装包不小（Windows 版约 260 MB，macOS 版约 500 MB），这是正常的——里面自带了一整套运行时，不需要你再装 Node.js、Python 之类的东西。

安装过程就是普通的"下一步"：

  1. Windows：双击 ...-Setup.exe。如果弹「Windows 已保护你的电脑」，点更多信息 → 仍要运行（这是自签名安装包的正常提示，不是病毒警告）。
  2. macOS：打开 .dmg，把图标拖进「应用程序」。第一次打开如果提示"无法验证开发者"，去系统设置 → 隐私与安全性，在下面点仍要打开。

方式 B：从官方源码跑（进阶，先跳过）

官方仓库是 deepseek-ai/deepseek-harness，按照它的 README.zh.md 里的步骤装依赖、启动 dsh，浏览器打开它打印的地址就是 Web UI。这条路需要你会用命令行，本文不展开。

第一次打开：三个概念必须先搞懂

很多人第一次用会被卡住，就卡在下面这三个词上，其实很简单：

1. 工作区（Workspace）——"AI 能看见哪个文件夹"

打开之后第一件事：点「选择工作区」，选一个文件夹。

这是新手最容易懵的地方：没选工作区之前，下面的输入框是灰的、点不动。不是软件坏了。

怎么选？原则是**"让 AI 只看它该看的"**：

  • 要让它修插件 → 就选放插件的那个目录（或者更上层一点，比如 D:\work）
  • 别一上来就选 C:\（整个硬盘），那样它每次列文件都要翻半天，而且风险更大

2. 会话（Session）——"一段对话 = 一个任务"

一个会话里你和 AI 的上下文是连续的，它会记得你前面说过什么。新任务开新会话，不要让"修插件"和"改简历"挤在一起，否则它会把两件事的信息搅在一起。

3. 权限审批（Approval）——"它要动手之前会问你"

AI 要读文件、改文件、跑命令时，会弹一个确认框告诉你它准备做什么。看清楚再点同意——这是你和 AI 之间的安全阀。

从零开始的第一句话，推荐就发这一句（真的可以复制粘贴）：

你好，我是第一次用。请先用一句话告诉我你是谁、能做什么，然后把这个工作区里的文件和目录结构列出来，用中文解释每个文件大概是干什么的。不要修改任何文件。

这句话同时做到三件事：确认工具通了、确认它看得见你的文件、明确禁止它动手（先只读，最安全）。

配置模型：填一个 Key 就完事

DSH 本身不含模型，它要连到 DeepSeek 的 API 才能思考。配置只有一步：

  1. 打开 设置（Settings）→ 模型（Models）
  2. 找到 DeepSeek 卡片，把 API 密钥粘进去，保存

不用重启，下一次请求就生效。

几个细节值得知道（都来自官方配置文档）：

  • 密钥是只写的。保存之后界面上只会显示脱敏后的描述，永远不会再给你看明文；密钥实际存在 $DSH_HOME/.credentials.yaml，配置文件里只留一个引用。这比很多工具把 Key 明文写在配置里要靠谱。
  • 想手动改配置：设置页顶部有「打开配置文件」，编辑的就是 $DSH_HOME/settings.yaml（Windows 上就是 C:\Users\你的用户名\.dsh\settings.yaml）。改完存盘即生效。
  • 要接公司网关 / 自建服务：设置 → 模型 → 添加自定义提供方，填 Provider ID、基础 URL、API 协议（openai-completions / openai-responses / anthropic-messages 三选一，必须和网关实际用的一致）、密钥，以及至少一个模型。
  • 填错 Key 的典型报错就是 MISSING_CREDENTIAL；模型名写错是 UNKNOWN_MODEL。

配好之后，随手验证一句（别省这一步）：

请回答：1+1 等于几？只回答数字。

秒回说明通了。如果转圈半天或者报错，先回设置页检查 Key 有没有多余空格、余额是不是 0。

第二部分：注册 DeepSeek、充值、拿 API Key

这一步看着琐碎，但它是唯一没法让 AI 代劳的一步（要你本人实名、要你付钱）。走一遍，五分钟。

1. 注册

浏览器打开：

https://platform.deepseek.com/

（这是「开放平台」，和网页版聊天入口 chat.deepseek.com 是两个站，别搞混——只有开放平台里才有 API Key。）

按页面提示用手机号或邮箱注册、登录。国内手机号直接收验证码即可。

2. 充值（不充值的话，第一次调用就报余额不足）

登录后进平台左侧菜单里的充值 / 费用相关页面（DeepSeek 的页面改版比较勤，认"充值""余额""Top up"这几个字就行）：

  1. 点充值
  2. 选金额。建议第一次充 ¥20（理由在下面）
  3. 支付宝 / 微信扫码付款
  4. 回到首页确认余额已经变了

充值规则有一条容易忽略的：赠送余额优先于充值余额被扣减。如果你之前领过赠送额度，会先花赠送的。

3. 创建 API Key（这一步的Key只显示一次）

打开：

https://platform.deepseek.com/api_keys
  1. 点「创建 API Key」
  2. 名字随便起，建议按用途起，比如 dsh-desktop
  3. 创建后立刻复制——这串 sk- 开头的字符串只会显示这一次，关掉就再也看不到了（丢了只能删了重建）

4. Key 的正确用法和红线

红线只有一条：API Key 等于你的钱包。 谁拿到都能花你的钱。

  • ✅ 粘进 DSH 的设置页（它只写不读，安全）
  • ✅ 需要放到环境变量时，写到本机环境变量里
  • ❌ 绝对不要粘到聊天窗口里发给别人
  • ❌ 绝对不要写进代码 / 提交到 GitHub（GitHub 上有机器人 7×24 扫 sk- 开头的字符串，几分钟内就能被刷爆）

万一泄露了：马上去 platform.deepseek.com/api_keys 把它删掉，再建一个新的。

5. 大概要花多少钱？（这是最关键的一问）

DeepSeek 是按 token 计费的（token ≈ 半个到一个汉字）。官方价格表（模型 & 价格，单位：元 / 百万 tokens）：

模型 输入（缓存命中） 输入（未命中） 输出
deepseek-flash 空闲时段 0.02 1 4
deepseek-flash 高峰时段 0.04 2 8
deepseek-v4-pro 空闲时段 0.15 4.5 13.5
deepseek-v4-pro 高峰时段 0.30 9.0 27.0

两个官方的小细节，直接帮你省钱：

  1. 空闲时段的价格是高峰时段的一半。北京时间周一至周五 9:00–12:00、14:00–18:00 是高峰（不含法定节假日）；其余时间、包括周末和节假日全天，都是空闲价。
  2. deepseek-flash 便宜到可以忽略。它上下文 1M、一次最多输出 384K，做本文这种"读代码 + 改代码"的活完全够用，新手默认就用它。要看更长的推理、更难的算法再换 deepseek-v4-pro。

那么本文这一整套活（解包两个安装包、读几千行 JS、写脚本、改代码、打包、验证）大概多少钱？

  • 输入大概几十万到一两百万 token（代码反复被读、且有缓存命中）
  • 输出大概几万到十几万 token

按 deepseek-flash 空闲时段算，总成本在几块钱人民币量级，一般不超过 ¥5。所以：

第一次充 ¥20 是够用很久的。别一上来充几百。

配好之后，你就可以用下面这套方法，让 AI 替你干活了。

第三部分：怎么"用嘴"让 AI 干完一整件活

这一部分是全文最值钱的部分。会写 prompt 的人，和不会写的人，拿到的东西差十倍。

先记四条心法（比任何 prompt 模板都重要）

① 一次只让它做一件事，先"读懂"，再"动手"。

新手最常犯的错是一句话把什么都交代了：

❌ "帮我看看这个插件哪里有问题，然后修好，再打包给我。"

它要么瞎改一通，要么先反问你十个问题。正确做法是分轮次：先看懂，再定位，再修，再打包，再验证。每一轮你都能检查它的结论对不对，错了就当场纠。

② 把"感觉"翻译成"可验证的事实"。

"上传失败"是感觉，"上传失败"不是需求。你要逼它给出事实：是哪个文件第几行、什么条件触发、有没有命令输出或日志能证明。本文全部结论都附了"文件 + 行号 + 可复现命令"。

③ 让它写脚本自证，而不是嘴上保证。

它说"我修好了"没有意义，它写一个 verify-crx.mjs 跑出来 ✅ PASS 才有意义。能跑的检查 > 口头保证。这也是后面能一眼看出"他们以为修好了其实没修好"的原因。

④ 让它自己交代"哪些验证过、哪些没验证过"。

最后一轮一定要问这句：

请明确列出：哪些结论是你真的验证过的（附命令和输出），哪些只是代码推理、还没在真实环境里验证过。

没有这句，AI 很容易把"我觉得应该是"讲成"就是"。本文下面那张结论表里，上传相关改动我标了"真机待验证"，就是因为这一问。

真实案例：三句抱怨 → 四类问题

起点：需求和素材

用户（客服转来的原话，一个字没改）：

明 上次那个新版他们说用不了 还有旧版也出一些问题 证书上传不成功，或者跳过之后第二遍再上传识别不到原来上传失败的好像

素材是两个文件：

C:\Users\jimmycppliu\Downloads\淘宝证书自动上传2.0.crx      ← 用户手上的"旧版"
<站点下载目录>\taobao-cert-uploader-v1.3.1-360-signed-v2.crx ← 对外发布的"新版"

第 1 轮：让它读懂这个 crx（不修改任何东西）

这个目录里有一个浏览器扩展包 淘宝证书自动上传2.0.crx。请：

  1. 先判断它是什么格式（注意：crx 不是普通的 zip，前面有一段头部，直接解压会失败），把它解包到 unpacked/ 目录；
  2. 列出完整的文件树和每个文件的大小；
  3. 画一张"用户操作 → 哪个文件在处理 → 调用了什么"的主流程图；
  4. 告诉我这个扩展一共几个版本、manifest 里的版本号是多少、涉及哪些淘宝域名。 全程只读，不要改任何东西。

这一步的价值：把"一个不知道谁写的 54KB 二进制包"变成"22 个文件、我能看懂的结构"。

顺便它就能发现第一个不合常理的地方：文件名写着「2.0」，但 manifest.json 里的 version 是 1.2.5。

代码里的文件名模板也是写死的：

filename: `淘宝证书自动上传2.0-${suffix}.crx`,

也就是说，"2.0"只是产品名，不是版本号。这件事后面影响很大。

第 2 轮：把模糊抱怨拆成可验证的假设

用户的原话是：「上次那个新版他们说用不了 还有旧版也出一些问题 证书上传不成功，或者跳过之后第二遍再上传识别不到原来上传失败的好像」

请把这句话拆成 3 条独立的、可以用代码或命令验证的技术假设，每条都要说清楚：

  • 假设是什么
  • 如果是真的，应该能在哪个文件的哪一段代码里看到证据
  • 用什么方法能证实或推翻它

现在先不要下结论，只列假设和验证方法。

它给出的三条（后来全部被证实）：

# 假设 验证方法
1 "新版用不了" = 安装包本身有问题（不是功能问题） 解析两个 crx 的文件头，看能不能通过 Chrome 的校验
2 "上传不成功" = 页面上找不到元素，或者按钮点不动却没报错 检查选择器是否写死绝对路径、点确定前有没有校验按钮状态
3 "第二遍识别不到" = 失败的单被误标成"已完成"，之后永久跳过 找"完成记录"的写入条件和过滤逻辑

第 2 轮是最容易被忽略、但收益最高的一轮。 它把一次"感觉驱动"的 debug，变成了三道有明确判定标准的判断题。

第 3 轮：找真凶（这一轮直接破案）

请写一个 Node 脚本 verify-crx3.mjs，输入一个 .crx 文件，输出：

  1. CRX 版本号、头部长度、zip 起始偏移；
  2. 从头部里解析出公钥（SPKI）和签名；
  3. 计算 crx_id = SHA256(公钥)[0:16]，并换算成 Chrome 的 32 位扩展 ID；
  4. 用 Chromium 的规则验签（components/crx_file/crx_verifier.cc 的 VerifyCrx3：载荷 = "CRX3 SignedData\0" + LE32(signed_header_data 长度) + signed_header_data + zip），输出验签结果。

然后分别跑这三个文件，把结果做成一张对照表。

跑出来的结果（这就是"一眼破案"）：

安装包 CRX 版本 验签 结论
用户手上的旧版（内部版本 1.2.5） 3 ✅ 通过 这个包是好的，能装
对外发布的第一个"新版"（v1.3.1-360.crx） 2 — ❌ Chrome 只接受 version 3，这个包必然安装失败
对外发布的第二个"新版"（v1.3.1-360-signed-v2.crx） 3 ❌ 失败 ❌ 签名载荷长度算错，照样装不上
修复后重新打的 1.4.0 3 ✅ 通过 可以发

第一个包的头部，字节级长这样：

43 72 32 34  02 00 00 00  00 00 00 00  50 4b 03 04 ...
 C  r  2  4   version=2    两个长度全0    PK..  (zip 从这里开始)

顺着这条线索回发布脚本一看，凶手自己招了：

// 旧版 publish-extension.mjs ：签名失败/找不到私钥时的"兜底"
const crx = Buffer.concat([Buffer.from('Cr24'), Buffer.from([2,0,0,0,0,0,0,0]), zipBuf]);

注释写着"退回无签名"，实际上是造了一个 Chromium 根本不认的伪格式。 这就是"新版用不了"四个字的全部真相——功能可能是好的，但包根本没装上。

而第二个包更冤：它动了手想修，注释还写着「参考 chromium 源码」，但把长度写成了整个 CrxFileHeader 的长度：

// ❌ 错误（1.3.1 的 utils/crx-pack.js）
new DataView(headerSizeLE.buffer).setUint32(0, placeholderHeader.length, true);
const signPayload = concatChunks([SIGNATURE_CONTEXT, headerSizeLE, signedData, zipBytes]);

正确写法是拿 signed_header_data 自己的长度（这里 18 字节，而不是 header 的 581 字节）：

// ✅ 正确
const headerSizeOctets = new Uint8Array(4);
new DataView(headerSizeOctets.buffer).setUint32(0, signedData.length, true);
const payload = concatChunks([SIGNATURE_CONTEXT, headerSizeOctets, signedData, zipBytes]);

长度差 563 个字节，签名自然验不过——"以为修好了"，比没修还危险。

这一轮我最想让你学到的不是 CRX 格式，而是："装不上"和"功能坏了"是两类完全不同的问题。 用户说"用不了"，团队一直以为是功能没做好，其实连门都没进去。

第 4 轮：修（外加自检）

根据上面的结论，请：

  1. 修正 utils/crx-pack.js 的签名载荷，并在打包函数内部加自检：签完立刻按 Chromium 规则验一遍，验不过就抛错，不许产出废包；
  2. 修改发布脚本：删掉"退回无签名"的回退分支，签名失败就整轮发布失败退出（宁可这版不发，也不要发一个装不上的包）；
  3. 针对另外两个功能问题，先给修复方案再改，每条都说明"改哪里、为什么、怎么验证"；
  4. 每改一处，都在同一轮里写一个不依赖浏览器、不依赖淘宝的自检用例。

它交回来的修复清单（对应三个抱怨）：

（1）"跳过之后第二遍识别不到" —— 根因是完成记录的判定太宽：

// ❌ 旧：只要有一条记录就当"做过"
if (records[key]) { skipped.push(...); } else { pending.push(...); }

// ✅ 新：只有"没跳过 + 没失败 + 至少成功一个证书"才算真的完成
function tcbIsCompletedShipRecord(record) {
  if (!record) return false;
  if (Number(record.certFailed) > 0) return false;
  if (record.skipReason === 'heartbeat-timeout') return false;
  if (record.skipReason === 'batch-consign') return true;   // 批量发货页确实没法处理
  if (record.noCertButtons) return false;                   // "没找到按钮" ≠ "没有证书"
  return Number(record.certUploaded) > 0 || Number(record.certSkipped) > 0;
}

外加一个一次性数据迁移：升级后自动把旧版写下的"假完成"记录清掉（不然那些单永远躺在黑名单里）。这比让人手工去点「清理异常记录」靠谱。

（2）"证书上传不成功" —— 加固三处：

  • 上传控件选择器原来是一条十几层 nth-child 的绝对路径，弹窗改版必挂。现在按「精确 → 放宽」四级兜底，全都不中就直接抛错说明尝试过哪些选择器。
  • 填完证书编号回读校验，注入图片后检查 input.files 长度——以前填失败也照样往下点「确定」。
  • 点「确定」前等按钮变成可点击；如果一直是禁用的，抛错并直接点名缺了什么：
throw new Error(`确定按钮不可点击：${reason}`);
// reason 例：'证书编号为空、检测机构未选择'

（3）"新版用不了" —— 修 crx-pack.js + 删掉发布脚本里的伪格式回退 + 加发布前门禁。

然后它写了自检脚本，跑出来是这样（这一段是真的跑过，不是示意）：

1) 完成记录判定 tcbIsCompletedShipRecord()  —— 「跳过之后第二遍识别不到」的根因
   ✅ 正常上传完成的记录 → 算完成
   ✅ 证书本来就都在（全部跳过）→ 算完成
   ✅ 【旧版 bug】本页没扫到证书按钮 → 不算完成，必须重试
   ✅ 有失败证书 → 不算完成，必须重试
   ✅ 心跳超时跳过 → 不算完成，必须重试
   ✅ 批量发货页跳过 → 算完成（确实没法处理，不用反复重试）
   ✅ 没有任何记录 → 不算完成
2) CRX3 签名（按 Chromium crx_verifier.cc 的规则）
   ✅ zip 本地文件头 = PK\x03\x04
   ✅ crx 魔数 = Cr24
   ✅ crx version = 3
   ✅ header 里声明的 crx_id = sha256(公钥 SPKI)[0:16]
   ✅ ✅ 正解：LE32(len(signed_header_data)) + signed_header_data + archive → 验签通过
   ✅ ❌ 1.3.1 的错误写法：LE32(整个 header 长度) → 验签失败（Chrome 拒绝安装）
   ✅ 篡改 archive 后验签失败

🎉 自检完成：通过 17 项，失败 0 项

注意第 8、9 行：它把"错误写法"也写成了一个用例。这样以后谁再手贱改回去，一跑测试就红了。这叫"把踩过的坑变成防线"。

第 5 轮：打包 + 发布前门禁

请再给我一个命令行打包脚本 tools/pack.mjs：

  1. 打包出 zip（给解压安装用）和签名 crx（给一键安装用）；
  2. 复用插件自己的 utils/zip-store.js 和 utils/crx-pack.js，不要在脚本里另写一份打包逻辑（两份实现必然分叉）；
  3. 打包完自动跑校验：解压 → 所有 js 做语法检查 → manifest 能不能解析 → crx 验签；
  4. 私钥从 ../tcb-keys/ 或 TCB_SIGN_KEY 读，永远不要打进安装包里。
  5. 任何一步失败就直接退出，不要"降级继续"。

第 6 轮：让它自己交代"没验证的部分"

请给我一份收尾报告，必须包含：

  1. 三个抱怨各自对应"改了什么文件、第几行"；
  2. 哪些结论是真机验证过的（附命令与输出），哪些只是代码推理；
  3. 用户升级时的注意事项（比如旧版要不要先卸载）；
  4. 还有什么风险没排除。

这一轮它给出了两个我必须转达给用户的点，都是不看代码就想不到的：

⚠️ 一：升级前必须先卸载旧版。 因为两个安装包用的是不同的签名私钥，扩展 ID 就不一样：

用户手上的旧版：9aca0f8fb12cde673f7112154193b181  → 扩展ID jkmkapiplbcmnoghdphbbcbfebjdlbib
对外发布的 1.3.1：065958202bcd28ca5dd35b88d426a902 → 扩展ID agfjficaclmncimkfnndfliinecgkjac

ID 不同 = 浏览器眼里它是两个不同的插件，不是"版本更新"。结果就是：新旧两个同时存在、同时往页面里加按钮和面板，互相打架。而且新插件的本地记录是空的（已完成订单、证书自增序号、白名单注入全部归零）。

所以修复版的签名策略是：用回旧版那把钥匙，这样老用户装上就是"同一个插件的升级"，记录都在。

⚠️ 二：私钥不该出现在安装包里。 旧版把签名私钥 utils/export-key.dat 直接打进 CRX 分发给所有人——等于把公章复印给每个用户。1.4.0 起不再随包分发，改用发布脚本在本地签名。

⚠️ 三（诚实交代）： 上传相关的三处加固是代码推理 + 单元自检级别的验证，没有在真实淘宝卖家页面上跑过端到端——因为那需要登录卖家和真实订单。所以 1.4.0 的第一件事是「小批量试」，并且出问题就用插件自带的「📦 导出日志包」把现场发回来。

这一点非常重要：一个靠谱的 AI 会明确告诉你它验证到哪一步了。 如果它拍着胸脯说"全部修好、保证没问题"，你反而要警惕。

第五部分：小白避坑清单（建议收藏）

关于 DeepSeek Harness

  1. 没选工作区，输入框是灰的 —— 不是坏了。
  2. 一个任务一个会话 —— 别把不相干的事混在一起。
  3. 新任务先只读 —— 第一句永远加"不要修改任何文件"。
  4. 权限弹窗要看清楚 —— 那是安全阀，不是烦人的广告。
  5. 模型先用 deepseek-flash —— 便宜、够用、上下文 1M。贵的不一定更适合你的活。
  6. 想省钱就挑空闲时段跑 —— 避开工作日 9:00–12:00、14:00–18:00，价格直接打五折。

关于 API Key

  1. Key 只显示一次，创建后立刻复制。
  2. 别往聊天窗口、代码、GitHub 里粘 Key，泄露了立刻去平台删掉重建。
  3. 第一次充 ¥20 就够跑很久，别一次充几百。

关于"让 AI 干活"

  1. 分轮次：读懂 → 定位 → 修 → 打包 → 验证，别一口气全交给它。
  2. 要证据：文件 + 行号 + 可复现命令，缺一不可。
  3. 要自检：让它写能跑的测试，别接受"我改好了"。
  4. 要它自己说边界：哪些验证过、哪些没验证。
  5. 拿不准就问"有没有更简单/更稳妥的方案"，它经常能给你省掉一半工作。
  6. 改完一定留一份"坑的测试" —— 把踩过的坑写成用例，下次谁改回去谁红。

关于发给自己用户的东西（血泪）

  1. "我能打开"不等于"用户能安装"。这次的教训是：先验证产物本身合法，再去 debug 功能。顺序反了，团队会花几天去修一个根本没被运行过的代码。
  2. 不要写"失败就降级成另一个格式"的兜底。伪格式比明确报错糟糕一百倍——它把"打包失败"变成了一次静默的、面向所有用户的故障。
  3. 尽量别换签名私钥。换了 = 换了扩展 ID = 对浏览器来说是新插件，老用户的本地数据全部丢失。
  4. 私钥是公章，不要随包分发。

附：修插件的过程中，顺手修掉的两个博客构建脚本坑

这两个不在需求里，是 AI 为了"能把自己的活验证完"而被迫发现的——这也是我把这类工具当日用工具的原因：它会把挡路的坑一起填了。

  1. scripts/cloudbase-build-stats.mjs 在 Windows 上读不到本地数据。 代码用 new URL('..', import.meta.url).pathname 取项目根目录，Windows 上会得到 /D:/work/blog/ 这种带前导斜杠的路径，于是 existsSync 永远为 false，本地构建静默丢掉全站 PV 和评论数据（页面上那些「👀 24」「💬 1」会变成占位符）。改成 fileURLToPath 后，本地构建也能正确复用 data/cloudbase-backup/latest.json。

  2. 同一天多篇文章的 urlKey 会随机器变化（localeCompare 的坑）。 文章 URL 是 /post/YYYYMMDD/，同一天的第二篇起叫 YYYYMMDD-2、-3……而决定"谁是第一篇"的那句排序用了 localeCompare。这个函数的结果跟运行机器的系统语言有关：中文 locale 按拼音排（谙 ān → 记 jì → 生 shēng），英文 locale 按码点排（生 U+751F → 记 U+8BB0 → 谙 U+8C19）。结果就是同一份代码在不同机器上构建，那几篇文章的网址会互换——对已有文章等于换了网址，SEO 和外部链接全废。改成码点比较后构建结果与机器无关（我用脚本对比了新旧映射表，旧文章 URL 变化数 = 0）。

顺带一条经验：凡是"排序 + 生成 ID/URL"的地方，都要警惕 locale、时区、文件系统返回顺序这三件事。 它们会让"同一份代码"在不同机器上产出不同结果，而且是静默的。

这篇文章里没有任何"魔法"。AI 做的事情，本质上是三件我们本来也要做的事，只不过它做得更快、更细、更不容易偷懒：

  1. 把抱怨变成假设（人容易跳过这一步，直接开始瞎试）
  2. 把假设变成可执行、可复现的证据（写脚本、解析字节、验签）
  3. 把结论变成不会再犯的防线（自检脚本 + 发布门禁）

所以哪怕你一句代码都不会写，你也能用这套方法：你负责"提出好问题、检查结论靠不靠谱"，它负责"读、算、改、验"。

最后再重复一遍那句最关键的：

让 AI 明确告诉你——哪些它验证过了，哪些它只是在猜。

这句话，比任何 prompt 技巧都值钱。
