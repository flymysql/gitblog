# 一、装 DSH（5 分钟）

**它是什么**：跑在你自己电脑上的 AI 助手。能读你指定的文件夹、能自己跑命令、动手前会问你。聊天机器人给你答案，它给你结果。

分两条路，小白走第一条：

| | 是什么 | 适合谁 |
| --- | --- | --- |
| **DSH Desktop**（推荐） | 社区维护的桌面客户端，**一键安装包，不需要命令行和 Node.js** | 绝大多数人 |
| 官方 Harness | [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 源码 / CLI | 开发者 |

打开官网 **<https://dshdesktop.cn>**，点「**为 Windows 下载**」或「**为 macOS 下载**」：

![DSH Desktop 官网：一键下载（为 Windows / 为 macOS 下载）](assets/uploads/2026/09/dsh-site-download.webp)

> 说明一下：**DSH Desktop 是社区独立维护的开源项目，不是 DeepSeek 官方产品**（官网自己也标了这句话）。想用官方版本就走上面那条 CLI 路线。旁边那个「下载 Next 版」是更新更快的分支，小白先用普通版。

装完双击打开，就是这个样子：

![DSH Desktop 真实界面：左边工作区与会话，右边对话区，底部能看到模型和 token 用量](assets/uploads/2026/09/dsh-desktop-chat.webp)

安装包 200~500 MB 是正常的（自带运行时，不用另装 Node.js）。

- Windows 弹「Windows 已保护你的电脑」→ **更多信息 → 仍要运行**
- macOS 提示无法验证开发者 → **系统设置 → 隐私与安全性 → 仍要打开**

## 第一次打开：只认这三个地方

1. **① 左下「选择工作区」** —— 选一个文件夹（比如放插件、放代码的那个目录）。
   **没选之前输入框是灰的、点不动，这不是坏了** —— 这是新手最容易卡住的地方。它只看得到你选中的那个文件夹。
2. **② 输入框** —— 选中工作区后才能输入。新任务的第一次提问，建议永远加一句 `先不要修改任何文件`。
3. **⚙ 设置 → 模型** —— 填 API Key（下一节）。

> 一个小习惯：**一个任务开一个新会话**，别把改插件和写周报混在一起。

# 二、配模型：注册 → 充值 → 取 Key（5 分钟）

从 <https://platform.deepseek.com/> 开始（注意：**和聊天版 `chat.deepseek.com` 不是一个站**，只有开放平台里才有 API Key）。

**第 1 步｜注册登录**：手机号收验证码，或者微信扫码。

![DeepSeek 开放平台登录页](assets/uploads/2026/09/ds-platform-login.webp)

**第 2 步｜充值**：左侧「充值」→ 选金额 → 支付宝 / 微信扫码。**第一次充 ¥20 就够用很久。**

![充值页：选金额后用支付宝或微信支付](assets/uploads/2026/09/ds-platform-recharge.webp)

**第 3 步｜创建 API Key**：左侧「API keys」→ 点右上角「创建 API key」。

![API keys 页：右上角就是「创建 API key」](assets/uploads/2026/09/ds-platform-apikeys.webp)

创建出来的那串 `sk-…` **只显示这一次**，立刻点「复制」：

![创建 API key 弹窗：出于安全原因，之后无法再次查看](assets/uploads/2026/09/ds-platform-createkey.webp)

> ⚠️ 它是你的钱包，**不要发给别人、不要粘进代码或 GitHub**（GitHub 上有机器人 7×24 扫这种字符串，几分钟就能刷爆）。泄露了立刻去 API keys 页删掉重建。

**第 4 步｜粘进 DSH**：**设置 → 模型 → DeepSeek 卡片粘 Key → 保存**。立即生效，不用重启；密钥只写不读（页面上只显示脱敏结果）。

![DSH 设置 → 模型：DeepSeek 卡片、API 密钥输入框、保存按钮](assets/uploads/2026/09/dsh-models-settings.webp)

**花多少钱？**（官方价，元 / 百万 tokens）

| 模型 | 输入（未命中） | 输出 |
| --- | --- | --- |
| `deepseek-flash` 空闲时段 | **1** | **4** |
| `deepseek-flash` 高峰时段 | 2 | 8 |
| `deepseek-v4-pro` 空闲时段 | 4.5 | 13.5 |

- 北京时间**周一至周五 9:00–12:00、14:00–18:00 是高峰**（不含法定节假日），其余时间**半价**
- 新手默认用 `deepseek-flash`：上下文 1M，做「读代码 + 改代码」完全够
- 本文这一整套活（解包、读几千行 JS、写脚本、改代码、打包、验证），**成本在几块钱量级**

配好后先验证一句，别省这一步：

> 请回答：1+1 等于几？只回答数字。

报错对照：`401` = Key 不对（检查空格）；`Insufficient Balance` = 该充值了；`MISSING_CREDENTIAL` = 回设置里重新保存一次。

# 三、直接抄的 prompt

![把活拆成 6 步](assets/uploads/2026/09/dsh-guide-05-prompt.webp)

**核心只有一句：一次只让它做一件事。** 别一句话交代完——"帮我看看这个插件哪里有问题，然后修好再打包给我"是新手最常犯的错，它要么瞎改，要么反问你十个问题。

下面 10 条按 6 步排好，把 `[方括号]` 里的内容换成你自己的就行。

## 第 1 步｜读懂（只读，不许改）

> 我完全不懂这个文件。请：
> 1. 先告诉我它是什么格式（注意 `[文件名]` 不是普通 zip，前面有一段头部）；
> 2. 解包 / 展开到 `[unpacked/]` 目录；
> 3. 列出完整文件树，每个文件用一句话说明用途；
> 4. 画一张「用户操作 → 哪个文件在处理 → 调用了什么」的主流程图。
>
> 全程只读，不要修改任何文件。

> 用大白话给我讲一遍 `[这个项目/这个脚本]` 是干什么的、数据是怎么流动的。假设我是一个完全不懂编程的人，不要贴大段代码。

## 第 2 步｜把抱怨拆成能验证的假设

> 用户原话是：「`[把抱怨原封不动粘进来]`」
>
> 请把它拆成 **3 条可以用代码或命令验证的技术假设**，每条写清楚：
> ① 假设是什么；② 如果是真的，应该在哪个文件、哪一段代码里看到证据；③ 用什么命令或脚本能证实或推翻它。
>
> 现在先不要下结论，只列假设和验证方法。

**这一步是全文收益最高的一步**：它把"感觉驱动"的 debug 变成三道有明确判定标准的判断题。

## 第 3 步｜让它写脚本自证

> 请写一个 Node 脚本 `[verify-xxx.mjs]`：输入 `[一个文件]`，输出 ① `[版本号/头部长度]` ② `[解析出的关键字段]` ③ `[校验结果]`。
>
> 然后分别跑这几个文件，把结果做成一张对照表。
>
> 不要只说"看起来没问题"——我要能自己复现的输出。

> 你的每条结论都要附**文件名 + 行号 + 可复现的命令或日志**。说不清楚的地方直接写"这里我不确定"，不要猜。

**这两条是本方法论的命根子**：能跑的检查 > 口头保证。

## 第 4 步｜修 + 自检

> 针对这个 bug，**先给我修复方案**（改哪个文件、为什么、怎么验证），我确认之后再动代码。

> 修完之后，每改一处都在同一轮里配一个**不依赖浏览器、不依赖网络**的测试用例；如果能把刚才那种"错误写法"写成必须失败的反例，就更好。

> 这个做法有没有更简单或更稳妥的方案？如果有，列出 2 个替代方案和取舍。

> 用 `[插件/项目]` 自己的打包代码，不要在脚本里另写一份实现——两份实现必然会分叉。

## 第 5 步｜打包 + 发布前门禁

> 给我一个命令行打包脚本 `[tools/pack.mjs]`：
> 1. 产出 `[新安装包]`；
> 2. **复用现有代码**，不要另写一份打包逻辑；
> 3. 打完自动解包、对每个 js 做语法检查、做 `[签名/哈希]` 校验；
> 4. 密钥只从仓库外面读，**绝不进安装包**；
> 5. 任何一步失败就直接退出，**不要"降级继续"**。

> 顺便告诉我：这个包要怎么验证"用户能装上"，给一条我能自己跑的命令。

## 第 6 步｜让它交代边界（每轮都该问）

> 请明确列出：哪些结论是你**真的验证过**的（附命令和输出），哪些只是代码推理、还没在真实环境里验证过。

> 给我一份收尾报告：① 每个问题对应"改了哪个文件、第几行"；② 哪些验证过、哪些没有；③ 用户升级要注意什么；④ 还有什么风险没排除。

**最后这一问最重要。** 一个靠谱的 AI 会告诉你"我验证到哪一步了"；如果它拍着胸脯说"全部修好、保证没问题"，反而要警惕。

# 四、这套 prompt 跑出来的结果

开头那句抱怨是客服转来的原话：

> 明 上次那个新版他们说用不了 还有旧版也出一些问题 证书上传不成功，或者跳过之后第二遍再上传识别不到原来上传失败的好像

素材就是两个文件：用户手上的 `淘宝证书自动上传2.0.crx`，和下载页上发布的 `taobao-cert-uploader-v1.3.1-360-signed-v2.crx`。**全程没打开过淘宝，也没登录过卖家账号**——只读代码 + 写脚本自证。

![新版用不了的字节级真凶](assets/uploads/2026/09/dsh-guide-06-bytes.webp)

![四个安装包的验签结果](assets/uploads/2026/09/dsh-guide-07-verify.webp)

| 抱怨 | 真因 | 状态 |
| --- | --- | --- |
| 新版用不了 | 发布的 crx 是 version=2 的伪头部，Chrome 直接拒装 | ✅ 修好 |
| 旧版也出问题 | 后来那个"签名修好了"的包，签名载荷长度算错，照样装不上 | ✅ 修好 |
| 证书上传不成功 | 上传控件选择器写死绝对路径、点确定前不校验按钮和编号 | ✅ 加兜底 + 回读校验 |
| 第二遍识别不到 | 失败单被误记为已完成，之后永久跳过 | ✅ 判定收敛 + 清理历史脏记录 |

新包已经放进 `cloudbase/static/packages/`，发到下载页只要一条命令：

```bash
node cloudbase/publish-extension.mjs --version 1.4.0
```

它自带门禁：**签名不对会直接失败退出，不会再发出去一个装不上的包。**

# 五、小白避坑清单

**用 DSH 的时候**

1. 没选工作区，输入框是灰的 —— 不是坏了
2. 一个任务一个会话
3. 新任务先只读，加一句"不要修改任何文件"
4. 权限弹窗看清楚再点，那是安全阀
5. 模型先用 `deepseek-flash`，便宜且够用
6. 想省钱就避开工作日 9–12、14–18

**关于 API Key**

7. Key 只显示一次，创建后立刻复制
8. 别往聊天框、代码、GitHub 里粘；泄露立刻删掉重建
9. 第一次充 ¥20 就够跑很久

**让 AI 干活**

10. 一次只让它做一件事，分 6 步推进
11. 要证据（文件 + 行号 + 可复现命令），不要"我觉得"
12. 要自检脚本，不要"我改好了"
13. 要它自己说清楚"哪些没验证过"
14. 把踩过的坑写成测试用例

**发给用户的东西**

15. "我能打开" ≠ "用户能安装"：**先验证产物合法，再去 debug 功能**，顺序反了会白干几天
16. 不要写"失败就降级成另一个格式"的兜底 —— 伪格式比明确报错糟糕一百倍
17. 尽量别换签名私钥，换了等于换了个新插件
18. 私钥是公章，不要随包分发

## 附：顺手修掉的两个博客构建脚本坑

这两个不在需求里，是 AI 为了能验证自己的改动而被迫发现的：

- **Windows 上读不到本地统计数据**：代码用 `new URL('..', import.meta.url).pathname` 取项目根目录，在 Windows 上会得到 `/D:/work/blog/` 这种带前导斜杠的路径，`existsSync` 恒为 false → 本地构建**静默丢掉全站 PV 和评论数据**。改用 `fileURLToPath`。
- **同一天多篇文章的网址会随机器变化**：决定 `YYYYMMDD-2`、`-3` 顺序的排序用了 `localeCompare`，它的结果跟**系统语言**有关（中文按拼音、英文按码点），同一份代码在不同机器上会把已有文章的网址互换。改成码点比较后，实测旧文章 URL 变化数为 0。

> 一条经验：**凡是"排序 + 生成 ID/URL"的地方，都要警惕 locale、时区、文件系统返回顺序这三件事。**
