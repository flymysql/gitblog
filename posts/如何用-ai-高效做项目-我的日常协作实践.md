> 过去两年，我大部分 side project 和基础设施类的工作，都是**人和 AI 一起完成的**——PeerCache、这篇博客的伪后台、几篇源码走读背后的 demo 分支，无一例外。效率提升是实实在在的，但踩过的坑也足够写一本错题集。
>
> 这篇文章不是"AI 能帮你写代码"的科普，而是把我日常协作里反复验证过的一套做法整理出来：**怎么拆任务、怎么给上下文、什么时候该 Plan、什么时候该新开对话、怎么让 Agent 自己跑完验证闭环**。如果你也在用 Cursor 或类似的 Agent 工具做项目，希望它能帮你少绕几圈弯。

---

## 一、先摆正位置：你管方向，AI 管执行

很多人第一次用 AI 写代码，心态大概是："我说一句，它把项目写完。"

现实往往相反：**你说一句，它写一段看起来对、跑起来错的代码**——然后你在 diff 里一行行找 bug，比自己写还累。

我后来换了一个更顺手的模型：

| 角色 | 你（人） | AI（Agent） |
|---|---|---|
| 核心职责 | 定目标、划边界、做取舍 | 读代码、改代码、跑命令、写测试 |
| 擅长的事 | 知道"要什么"和"不要什么" | 在已知模式里快速产出、批量重构 |
| 不擅长的事 | 记住几千个文件的细节 | 猜你没说清楚的隐含约束 |
| 最终责任 | **合并进主分支之前，你签字** | 提供可审查的候选方案 |

一句话：**AI 是执行力很强的协作者，不是产品经理，也不是架构师。** 你仍然要负责"做什么"和"做到什么程度算完"，它负责"怎么在当前代码库里落地"。

这套分工听起来像废话，但它直接决定后面所有技巧有没有用——如果你把"想清楚"这一步也丢给 AI，后面所有"高效"都是假象。

## 二、核心工作流：Plan → Context → Execute → Verify → Iterate

不管项目大小，我日常基本都走这五步。可以把它理解成一条**有验收标准的流水线**，而不是"聊天式写代码"。

```
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │   Plan   │───►│ Context  │───►│ Execute  │───►│  Verify  │───►│ Iterate  │
  │  想清楚   │    │  给够上下文 │    │  让它动手  │    │  跑验证    │    │  小步修正  │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
       ▲                                                              │
       └──────────────── 验收不过，回到 Plan 或 Context ────────────────┘
```

### 2.1 Plan：先规划，再生成

**Plan 是最省时间的一步，也是最容易被跳过的一步。**

Cursor 里可以 `Shift+Tab` 切到 Plan Mode：Agent 会先搜代码库、问澄清问题、输出一份带文件路径和改动点的计划，**等你点头才开始写代码**。我的经验：

- **新功能 / 跨模块改动 / 你不熟悉的代码区域** → 几乎总是先 Plan
- **改个 typo、调个常量、补一条已有模式的测试** → 可以直接 Agent
- **Plan 跑偏了** → 不要在一堆错误代码上修修补补；**回滚，改 Plan，重跑**。这比"继续聊"快得多

Plan 写好后我会做两件事：

1. **删掉 AI 过度设计的步骤**（比如"顺便重构整个模块"——这种一律砍）
2. **补上它没问到的约束**（性能要求、不能动的接口、必须兼容的旧行为）

> 把 Plan 存到 `.cursor/plans/` 是个好习惯。下次中断、换对话、或者开 Background Agent，都有据可查。

### 2.2 Context：给对上下文，比写长 prompt 重要

Agent 自带 `grep` 和语义搜索，**你不一定需要 `@` 每一个文件**。但有几类上下文，主动给比让它猜靠谱得多：

| 上下文类型 | 什么时候给 | 怎么给 |
|---|---|---|
| **目标文件 / 模块** | 你知道改哪里 | `@src/foo/bar.cpp` |
| **参考实现** | "照着这个模式做" | `@已有功能的类似文件` + 一句话说明差异 |
| **约束文档** | 项目有 Rules / AGENTS.md | 写进 `.cursor/rules/`，自动注入 |
| **分支 / PR 范围** | Code Review、补测试 | `@Branch` 或贴 PR 链接 |
| **失败信息** | 调试 | 完整报错 + 你怀疑的方向（哪怕只是猜测） |

**反模式**：把半本设计文档粘贴进对话，然后问"帮我实现"。信息量大不等于有效——Agent 会在无关细节里迷路。更好的做法是：**Plan 阶段给架构约束，Execute 阶段只给当前步骤需要的文件。**

### 2.3 Execute：任务粒度要小，边界要硬

AI 最怕的不是难，而是**模糊**。我把任务拆到满足下面几条才交给 Agent：

- [ ] **单一目标**：一次对话只做一件事（"加 RPC 接口"可以，"加接口顺便重构存储层"不行）
- [ ] **可验证的完成标准**："编译通过 + 单测覆盖 happy path"，而不是"尽量做好"
- [ ] **明确的不做清单**：`不要改 public API`、`不要引入新依赖`、`不要动 legacy 路径`
- [ ] **时间盒**：如果一个 Plan 步骤预估超过 ~30 分钟 Agent 工作量，继续拆

举个真实的拆法——"给 PeerCache 加一个 metrics 导出端点"：

```
❌ 坏 prompt：
   "给 PeerCache 加 metrics，要完善，跟业界最佳实践对齐。"

✅ 好 prompt：
   "在 PeerCache 的 HTTP admin 端口加一个 /metrics 端点。
    只导出 GET 吞吐和 P99 延迟两个 counter/histogram。
    格式用 Prometheus text exposition。
    参考现有 /health 的路由注册方式（@src/admin_server.cpp）。
    不要改 RDMA 数据路径，不要加新依赖。"
```

### 2.4 Verify：让 Agent 自己跑完验证闭环

**"写完"不等于"做完"。** 我要求 Agent 在声称完成之前，至少跑一轮：

1. **编译 / 构建**（`cmake --build`、`npm run build`……）
2. **相关测试**（优先单文件/单测，别一上来跑全量 CI）
3. **Lint / 类型检查**（如果项目有）
4. **对照 Plan 逐条勾选**

Cursor Agent 能跑终端、读输出、根据报错继续改——**你要做的是在 Rules 里写清楚这些命令是什么**，而不是每次口头提醒。

我在 `.cursor/rules/` 里通常会放：

```markdown
# 构建与验证

- 改 C++ 后：`cmake --build build -j` 然后 `ctest --test-dir build -R <相关测试>`
- 改前端后：`npm run build`，不要 `npm run dev` 除非我明确要求
- 改完必须自己跑 lint；不要让我来发现编译错误
- 不要声称"完成"直到构建和测试通过
```

### 2.5 Iterate：小步提交，而不是攒大招

每完成一个可验证的小步骤，就 **commit + push**。好处：

- Agent 搞砸了，你可以 `git revert` 而不是手动抠 diff
- Background Agent / Cloud Agent 可以基于最新代码继续
- PR 粒度小，Review 时人类（包括你自己）看得懂

我的习惯是：**一个 Plan 步骤 = 一个 commit message**，message 写清楚"做了什么"和"为什么"，方便以后 `@Past Chats` 或新对话续上。

## 三、上下文的长期建设：Rules、AGENTS.md、Skills

单次对话的 `@文件` 是战术；**项目级的 Rules 和文档是战略**。

### 3.1 `.cursor/rules/`：项目的"肌肉记忆"

Rules 是每次对话都会注入的静态上下文。适合放：

- 构建 / 测试 / 部署命令
- 代码风格里** linter 管不了的**部分（比如"错误处理统一走 `Status::Or` 模式"）
- 目录约定（"API 路由放 `app/api/`，别放 `lib/`"）
- 指向**权威示例文件**的指针（"组件结构参考 `components/Button.tsx`"）

不适合放：

- 整本 style guide（交给 linter）
- 所有命令的百科全书（Agent 知道常见工具）
- 极少触发的 edge case 清单

**原则：Rules 要短、要准、要跟着代码一起 version control。** 团队项目里，`.cursor/rules/` 应该和 `.clang-format` 一样提交到 git——这是"AI 时代的编码规范"。

### 3.2 `AGENTS.md`：给 Agent 看的 README

如果 Rules 是"做事的规矩"，`AGENTS.md` 就是"项目的地图"。我一般在里面写：

- **架构概览**：模块怎么连、数据怎么流
- **关键路径**：一条请求从入口到出口的 trace
- **测试策略**：怎么跑、测什么、mock 边界在哪
- **常见坑**：新人（和 AI）最容易踩的雷
- **安全红线**：哪些操作绝对不能做

`AGENTS.md` 的价值在于：**换一个新 Agent、开一个全新对话，它也能在 30 秒内建立正确的 mental model。** 这比每次重复解释"我们项目比较特别"省太多时间。

### 3.3 Skills：按需加载的专项能力

Cursor 的 Skills（`SKILL.md`）适合封装**特定工作流**——比如 Figma 设计转代码、生成架构图、跑 release 脚本。和 Rules 的区别：

| | Rules | Skills |
|---|---|---|
| 加载时机 | 每次对话 | Agent 判断相关时才加载 |
| 适合内容 | 通用规范 | 专项流程 / 工具链 |
| 上下文成本 | 始终占用 | 按需，更省 token |

## 四、对话管理：什么时候新开，什么时候续聊

这是日常最高频的问题之一。我的判断标准：

**新开对话：**

- 切换到**不同的 feature / bug**
- Agent 开始**重复犯同一个错**，说明上下文已经"污染"了
- 上一个任务已经 **commit 完**，下一个任务边界清晰
- 对话已经很长（体感超过 15~20 轮），回答质量明显下降

**继续当前对话：**

- 还在**同一个 feature 上迭代**
- 调试**刚改完的东西**（Agent 记得它为什么那么改）
- 需要引用**前几轮的尝试和失败原因**

续聊时用 `@Past Chats` 指向旧对话，比复制粘贴整段聊天高效——Agent 会按需提取，而不是把噪声全塞进来。

## 五、三种协作模式，按场景选

不是所有任务都适合同一种打开方式。我日常 roughly 分三档：

| 模式 | 适用场景 | 你怎么参与 |
|---|---|---|
| **Inline / Tab 补全** | 写函数体、补样板、改几行 | 实时看着，像结对编程 |
| **Chat / Agent（同步）** | 单模块功能、调试、重构 | 给 Plan，等验证，Review diff |
| **Background / Cloud Agent（异步）** | 独立 issue、文档、测试补全、迁移脚本 | 写清楚 issue 描述和验收标准，去干别的，回来 Review PR |

**Background Agent 特别适合"边界清晰、不太需要来回问"的任务**——比如"给这个模块补单元测试"、"按模板写迁移脚本"、"根据 issue 描述修一个已知 bug"。

关键是 issue / prompt 里写清：

```markdown
## 目标
……

## 验收标准
- [ ] ……
- [ ] ……

## 约束
- 不要 ……
- 参考 ……

## 相关文件
- `src/...`
```

Cloud Agent 会自己建分支、commit、push、开 PR——**你的主要工作变成 Review，而不是盯屏幕。**

## 六、Review：人仍然不可省略的一环

AI 写的代码，我会按下面清单过一遍（也写进了自己的协作备忘里）：

### 6.1 正确性

- [ ] 是否**真的**跑过测试，还是只在文字里说"应该没问题"
- [ ] 边界条件：空输入、错误路径、并发 / 资源释放
- [ ] 有没有**静默改行为**——尤其是"顺便 refactor"带来的

### 6.2 范围

- [ ] diff 里有没有**超出任务范围**的改动
- [ ] 有没有引入**不必要的新依赖**
- [ ] 注释 / 文档是不是**过度**了（AI  loves 写废话注释）

### 6.3 项目一致性

- [ ] 命名、错误处理、日志风格是否和周围代码一致
- [ ] 有没有违反 Rules 里写的约定

### 6.4 安全

- [ ] 密钥、token、内部 URL 有没有被写进代码或 commit
- [ ] 用户输入有没有直接拼进命令 / SQL / 路径

**PR 描述让 Agent 写初稿可以，合并前必须自己读懂 diff。** 这不是不信任 AI——而是最终责任在你。

## 七、常见反模式（错题集）

踩过坑才写得出来：

| 反模式 | 后果 | 怎么改 |
|---|---|---|
| **模糊大任务**（"优化一下性能"） | Agent 乱改一气，性能没涨 bug 多了 | 给指标、给 profile 结果、给范围 |
| **不 Plan 直接写** | 架构跑偏，返工成本 ×3 | 跨模块改动强制 Plan |
| **在错误实现上修修补补** | 越聊越乱，上下文全噪 | 回滚 → 改 Plan → 重跑 |
| **手动 `@` 一堆无关文件** | Agent 抓错重点 | 给目标文件 + 让它自己搜 |
| **不设"不做清单"** | "顺便"重构、顺便加功能 | 每条 prompt 写清 don'ts |
| **不跑验证就合并** | CI 红了再回头查 | Rules 里写死验证命令 |
| **对话太长不新开** | 回答质量断崖式下跌 | 完成一个 unit 就新开 |
| **把 AI 当 Google** | 得到过时或编造的 API | 让它在当前代码库里 grep，而不是凭记忆写 |

## 八、一个完整示例：从 issue 到 PR

假设 issue 是："博客搜索框在移动端键盘弹出时会遮挡结果列表。"

**第 1 步 · Plan（同步 Agent）**

```
@post.html @assets/css/post.css @assets/js/site.js

移动端搜索框键盘弹出时会遮挡结果。先分析原因，给出修复 Plan。
约束：不要改桌面端布局；不要引入新依赖；改 CSS 优先于 JS。
```

Agent 输出 Plan：定位到 `100vh` + 软键盘的问题，建议改用 `dvh` + 调整 `.search-results` 的 `max-height`。

我删掉 Plan 里"顺便重构搜索逻辑"的步骤，批准剩余部分。

**第 2 步 · Execute + Verify**

Agent 改 CSS，本地 build，在 Rules 指定的验证流程里确认静态资源无报错。

**第 3 步 · Commit + PR**

```
fix: 修复移动端搜索键盘遮挡结果列表

- 搜索层高度从 100vh 改为 100dvh
- 结果列表 max-height 跟随可视区域动态计算
- 桌面端布局无变化
```

**第 4 步 · 我 Review**

打开 PR，看 diff 只有 2 个文件、十几行，对照 Plan 勾选验收，合并。

全程可能 20 分钟。**如果没有 Plan，Agent 很可能"顺便"把搜索逻辑重写成 React 组件——然后你花两小时把它改回来。**

## 九、写在最后

用 AI 高效做项目，核心不是"prompt 技巧"，而是**工程纪律**：

1. **你先想清楚**（Plan）
2. **你给够上下文，但不给噪声**（Context / Rules / AGENTS.md）
3. **你拆小任务、划硬边界**（Execute）
4. **你要求验证闭环**（Verify）
5. **你小步提交、认真 Review**（Iterate）

AI 把"从想法到可运行代码"的路径缩短了，但**没有缩短"从可运行到正确、可维护"的路径**。后者仍然需要你知道项目要什么、能看懂 diff、能在它跑偏时及时喊停。

如果你也在摸索自己的协作备忘，建议从这三件事开始：

- 给当前项目写一份短的 `AGENTS.md`（哪怕只有半页）
- 在 `.cursor/rules/` 里加上构建和测试命令
- 下一次跨模块改动，强制先走一遍 Plan Mode

这三步不花钱，但通常能立刻少踩一半的低级坑。
